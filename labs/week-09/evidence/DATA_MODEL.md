# การออกแบบและโครงสร้างฐานข้อมูล Campus Service Request

## 1. ภาพรวม
ระบบจัดการคำร้องใช้ฐานข้อมูลเชิงสัมพันธ์ (Relational Database) ประกอบด้วย 2 ตารางที่มีความสัมพันธ์แบบ **One-to-Many (1:N)**:
- ผู้ใช้ 1 คน (`users`) สามารถสร้างคำร้อง (`requests`) ได้หลายรายการ
- คำร้องแต่ละรายการ (`requests`) ต้องเป็นของผู้ใช้คนใดคนหนึ่งเท่านั้น โดยเชื่อมโยงผ่าน Foreign Key (`requester_id`)

## 2. ทำไมต้องแยกเป็น 2 ตาราง

ในสัปดาห์ที่ 06–07 ระบบเก็บข้อมูลคำร้องเป็นก้อนเดียวในไฟล์ JSON โดยฝังชื่อผู้แจ้ง (`requesterName`) ลงในทุกคำร้อง หาก "สมชาย ใจดี" ส่งคำร้องไว้ 20 รายการ แล้ววันหนึ่งเปลี่ยนชื่อหรือนามสกุล **จะต้องตามแก้ข้อมูลมากถึง 20 ที่** ซึ่งส่งผลให้เกิดปัญหาสำคัญตามหลักฐานข้อมูลดังนี้:

1. **เกิดข้อมูลซ้ำซ้อนโดยไม่จำเป็น (Data Redundancy):** ข้อมูลชื่อและแผนกของผู้ใช้คนเดิมถูกบันทึกซ้ำทุกครั้งที่สร้างคำร้อง ทำให้เปลืองพื้นที่จัดเก็บโดยเปล่าประโยชน์
2. **ปัญหาการแก้ไขข้อมูลไม่ครบถ้วน (Update Anomaly):** หากผู้ใช้แจ้งเปลี่ยนชื่อ แต่ระบบแก้ไขไม่ครบทุกแถว จะทำให้เกิดภาวะข้อมูลขัดแย้งกัน (Inconsistent State) โดยในระบบจะมีทั้งชื่อเก่าและชื่อใหม่ปะปนกัน
3. **ไม่สามารถจัดเก็บข้อมูลเพิ่มเติมของผู้ใช้ได้อย่างมีประสิทธิภาพ:** หากต้องการเพิ่มข้อมูลส่วนตัว เช่น เบอร์โทรศัพท์ หรืออีเมล จะต้องเพิ่มคอลัมน์และกรอกซ้ำลงไปในทุกแถวของคำร้อง
4. **ความผิดพลาดจากการพิมพ์ (Human Error):** หากผู้ใช้พิมพ์ชื่อผิดเล็กน้อย เช่น "สมชย ใจดี" ระบบจะมองว่าเป็นคนละคนทันทีเนื่องจากเป็นเพียงข้อความธรรมดา

**การแก้ปัญหา:** การแยกตาราง `users` ออกมาเป็นสัดส่วน และให้ตาราง `requests` เก็บเพียง `requester_id` ชี้มา จะทำให้ข้อมูลผู้ใช้ถูกจัดเก็บอยู่ที่เดียวอย่างเป็นเอกเทศ (Single Source of Truth) เมื่อมีการเปลี่ยนชื่อหรือแก้ไขข้อมูล ก็แก้เพียงแถวเดียวในตาราง `users` แล้วทุกคำร้องที่อ้างอิงถึงจะสะท้อนข้อมูลที่ถูกต้องโดยอัตโนมัติ

## 3. รายละเอียดตาราง

### ตาราง `users` (ตารางหลักสำหรับเก็บข้อมูลผู้ใช้งาน)
| คอลัมน์ | ชนิดข้อมูล | Constraint | เหตุผล |
| :--- | :--- | :--- | :--- |
| `id` | `INTEGER` | `PRIMARY KEY AUTOINCREMENT` | ใช้เป็นตัวระบุตัวตนของผู้ใช้ (Surrogate Key) แบบตัวเลข ลำดับเพิ่มขึ้นอัตโนมัติ และค้นหาได้รวดเร็ว |
| `name` | `TEXT` | `NOT NULL` | ชื่อ-นามสกุลของผู้ใช้ จำเป็นต้องมี ห้ามเว้นว่าง |
| `department` | `TEXT` | `NOT NULL` | สังกัด/แผนกวิชาของผู้ใช้ จำเป็นต่อการประสานงาน ห้ามเว้นว่าง |
| `email` | `TEXT` | `NOT NULL UNIQUE` | บัญชีอีเมลสำหรับติดต่อ ต้องห้ามว่างและห้ามซ้ำกันในระบบ |

### ตาราง `requests` (ตารางเก็บรายการคำร้องบริการ)
| คอลัมน์ | ชนิดข้อมูล | Constraint | เหตุผล |
| :--- | :--- | :--- | :--- |
| `id` | `TEXT` | `PRIMARY KEY` | รหัสคำร้องที่สื่อความหมายสำหรับมนุษย์ เช่น `REQ-001` ห้ามซ้ำกัน |
| `requester_id` | `INTEGER` | `NOT NULL, REFERENCES users(id)` | Foreign Key บังคับว่าคำร้องต้องระบุผู้แจ้ง และต้องชี้ไปยังผู้ใช้ที่มีตัวตนอยู่จริงในตาราง users |
| `request_type` | `TEXT` | `NOT NULL, CHECK (request_type IN ('แจ้งซ่อม','บริการบัญชีผู้ใช้','ขอใช้อุปกรณ์','อื่น ๆ'))` | ประเภทคำร้อง บังคับเลือกตามประเภทที่ระบบรองรับเท่านั้น |
| `location` | `TEXT` | `NOT NULL` | สถานที่เกิดปัญหา เช่น อาคารหรือห้อง ห้ามเว้นว่าง |
| `details` | `TEXT` | `NOT NULL` | รายละเอียดปัญหาหรือสิ่งที่ต้องการ ห้ามเว้นว่าง |
| `priority` | `TEXT` | `NOT NULL DEFAULT 'normal', CHECK (priority IN ('normal','urgent'))` | ระดับความสำคัญ มีค่าเริ่มต้นเป็น normal และจำกัดเฉพาะค่าที่กำหนด |
| `status` | `TEXT` | `NOT NULL DEFAULT 'pending', CHECK (status IN ('pending','in-progress','completed'))` | สถานะของคำร้อง เริ่มต้นเป็น pending และจำกัดเฉพาะ 3 สถานะนี้ |
| `created_at` | `TEXT` | `NOT NULL DEFAULT (datetime('now','localtime'))` | บันทึกวันและเวลาที่ส่งคำร้องตามเวลาท้องถิ่นโดยอัตโนมัติ |

## 4. เหตุผลของการเลือกการออกแบบ

### 1. ทำไม `users.id` กับ `requests.id` จึงใช้ชนิดข้อมูลต่างกัน (INTEGER กับ TEXT)?
- **`users.id` (INTEGER):** ถูกออกแบบเป็น Internal Surrogate Key สำหรับการทำงานภายในระบบฐานข้อมูล การใช้จำนวนเต็ม (INTEGER) ร่วมกับ `AUTOINCREMENT` ช่วยให้ฐานข้อมูลจัดการลำดับได้เร็ว ประหยัดเนื้อที่ในการทำ Index และลดขนาดหน่วยความจำเมื่อนำไปทำ Foreign Key
- **`requests.id` (TEXT):** ถูกออกแบบเป็น Business Key หรือ Natural Key ที่ต้องแสดงผลให้มนุษย์นำไปสื่อสาร เช่น การแจ้งหมายเลขติดตามงาน `REQ-001` กับช่างซ่อม การมีตัวอักษรนำหน้าช่วยบ่งบอกประเภทของเอกสารได้ชัดเจน จึงต้องจัดเก็บเป็น `TEXT`

### 2. ทำไมต้องมี CHECK Constraint ในฐานข้อมูล ทั้งที่ API Backend ก็ตรวจข้อมูลอยู่แล้ว?
- เพื่อปฏิบัติตามหลักการ **Defense in Depth (การป้องกันหลายชั้น)**
- ฝั่ง Backend ตรวจสอบข้อมูลเพื่อตอบ HTTP 400 ให้แก่ผู้ใช้งาน แต่ฐานข้อมูลถือเป็นปราการด่านสุดท้าย (Single Source of Truth) ที่ต้องมีหน้าที่ปกป้องความสมบูรณ์ของข้อมูล (Data Integrity) ด้วยตนเองเสมอ ป้องกันข้อผิดพลาดในกรณีที่มีการรัน Database Migration, การรันคำสั่ง SQL ผ่าน CLI โดยตรง, หรือมี Service อื่นมาเชื่อมต่อฐานข้อมูลโดยไม่ผ่าน API เส้นเดิม

## 5. ตัวอย่างการ JOIN

คำสั่ง SQL ในการดึงข้อมูลคำร้องพร้อมชื่อผู้แจ้ง:

```sql
SELECT r.id,
       u.name AS requesterName,
       r.request_type AS requestType,
       r.location,
       r.status
FROM requests r
JOIN users u ON r.requester_id = u.id
ORDER BY r.id;

---

## 6. ข้อสังเกตสำคัญสำหรับการส่งต่อสู่สัปดาห์ที่ 10

จากการเปรียบเทียบผลลัพธ์ของคำสั่ง SQL JOIN:
```text
REQ-001 | สมชาย ใจดี | pending

กับโครงสร้างข้อมูล JSON ที่ API Contract ส่งไปยัง React Frontend ในสัปดาห์ที่ 07:

JSON
{ 
  "id": "REQ-001", 
  "requesterName": "สมชาย ใจดี", 
  "status": "pending" 
}
`

ข้อสังเกตและข้อสรุป:

โครงสร้างการจัดเก็บข้อมูลภายในฐานข้อมูล (Internal Database Schema) ไม่จำเป็นต้องเหมือนกับรูปแบบข้อมูลที่ส่งออกให้ผู้บริโภคข้อมูล (API / Client Contract)

ในฐานข้อมูลเราจัดเก็บแบบแยกตารางตามหลัก Normalization เพื่อลดความซ้ำซ้อนและรักษาความถูกต้อง แต่เมื่อจะส่งข้อมูลออกไปแสดงผลที่ Frontend เราสามารถใช้ SQL JOIN ร่วมกับการตั้งชื่อคอลัมน์ใหม่ด้วย AS เพื่อแปลงข้อมูลให้อยู่ในโครงสร้างที่ Frontend คาดหวังได้ทันที

นี่คือบทบาทหน้าที่สำคัญของ Service Layer ใน Backend ซึ่งในสัปดาห์ที่ 10 ตัว requestService.js จะเปลี่ยนจากการอ่าน JSON มาใช้คำสั่ง SQL JOIN ชุดนี้เพื่อส่งข้อมูลออกไปโดยไม่ต้องแก้โค้ดฝั่ง Controller หรือ Frontend เลย
